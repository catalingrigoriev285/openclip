Features

Everything a recorder should do. Nothing it shouldn't.

A classic recorder layout — toolbar on top, navigation on the left, pages on the right — with a live preview of exactly what you'll get.

Monitor, window or region

Record a whole display, a single window, or drag a rectangle on screen. Regions are cropped on the GPU on Windows, so the encoder only ever sees the pixels you asked for.

System audio + mic

Capture what you hear, what you say, or both. Streams are mixed on one timeline and resampled to 48 kHz stereo.

Live preview

See exactly what is being recorded — including the mouse cursor — before and while you record.

Standard MP4 that plays everywhere

H.264 video and MP3 audio in a plain, non-fragmented MP4 — opens in VLC, Windows Media Player, Movies & TV, Chrome, Edge and every ffmpeg-based tool. Files over 4 GiB are handled with co64.

No external runtime

OpenH264 and LAME are compiled from bundled sources at build time. The MP4 muxer is in-house.

Timing you can trust

Every frame carries its real capture timestamp. Frames are dropped — never desynchronised — if the encoder falls behind.

Simple controls

Frame rate, bitrate, full or half size, mic device, output folder and file-name prefix. That's the whole settings page.

Platforms

Builds on the three desktops.

You need a Rust toolchain (edition 2024 → Rust 1.85+) and a C/C++ compiler for the bundled codecs.

Requirements
Windows
Visual Studio Build Tools (MSVC). Nothing else. Capture uses native Windows.Graphics.Capture; system audio via WASAPI loopback.
macOS
Xcode command-line tools, plus autoconf automake libtool (LAME builds via autotools). macOS 13+ for capture; system-audio loopback needs macOS 14.6+.
Linux
build-essential autoconf automake libtool and the dev headers used by eframe / xcap / cpal: libxcb-render0-dev libxcb-shape0-dev libxcb-xfixes0-dev libxkbcommon-dev libssl-dev libxcb1-dev libxrandr-dev libdbus-1-dev libpipewire-0.3-dev libasound2-dev. X11 only for now.
Installing nasm before building enables OpenH264's assembly kernels and roughly doubles encoder throughput. Without it the build silently falls back to C.
How it works

One pipeline, no detours.

Frames go from the capture backend to a file without touching a system codec.

CaptureWindows.Graphics.Capture · xcap
Encode threadBGRA → I420 (SIMD)
OpenH264screen-content, real-time
MP4 muxerin-house, streaming
.mp4ftyp / mdat / moov
cpal mic / loopback→mixer · 48 kHz stereo→LAME MP3→muxer
Capture
Windows uses Windows.Graphics.Capture via windows-capture (BGRA frames, GPU-side crop for regions). macOS and Linux/X11 use xcap's video recorder for monitors and screenshot polling for windows.
Video
BGRA/RGBA → I420 with the SIMD yuv crate, then OpenH264 in screen-content real-time mode. Annex-B output becomes AVCC length-prefixed samples; SPS/PPS go into avcC.
Audio
Each cpal stream pushes timestamped chunks. The mixer places them on the recording timeline — inserting silence for gaps such as WASAPI loopback going quiet — resamples, and feeds LAME. Each MP4 sample is exactly one 1152-sample MP3 frame.
Mux
A streaming, non-fragmented MP4 writer with per-sample durations from real timestamps, a keyframe table, 0.5 s interleaved chunks and co64 for large files. Output is round-tripped through the independent mp4-atom parser in tests.
Get started

Two commands.

Clone, build in release mode, run. Output lands in ~/Videos as <prefix>-YYYYMMDD-HHMMSS.mp4.

Build & run
$ git clone https://github.com/catalingrigoriev285/openclip.git
$ cd openclip
$ cargo build --release
$ ./target/release/openclip
Headless examples
# record the primary monitor for 10 s
$ cargo run --release --example capture_to_mp4 -- 10 out.mp4

# encoder throughput on synthetic content
$ cargo run --release --example bench_encode -- 1920 1080 5

Known limitations

Honest about v1.

Wayland is not supportedAn xcap limitation — use an X11 session on Linux.
Window capture on macOS / Linux polls screenshotsSlower than monitor capture. On Windows it is native.
System audio on Linuxcpal has no loopback API; select a PulseAudio / PipeWire monitor source as the input device instead.
Resizing a captured window mid-recordingFrames of the new size are skipped; the encoder keeps the original dimensions.
Without nasm, OpenH264 manages roughly 25–30 fps at 1080p on high-entropy content on a modern desktop CPU; typical desktop content is much cheaper. Use "Half size" or a lower frame rate if you see drops.
